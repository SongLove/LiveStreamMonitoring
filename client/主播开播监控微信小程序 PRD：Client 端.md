# 主播开播监控微信小程序 PRD：Client 端

**文档版本**：V1.0
**编制日期**：2026 年 8 月 19 日
**适用范围**：微信小程序用户端，uni-app + Vue3 + TypeScript
**关联系统**：NestJS Server、MongoDB、Redis、Admin 管理后台

---

## 1. 文档说明

本 PRD 用于定义主播开播监控小程序的用户端产品范围、页面、交互、客户端职责、接口依赖和验收标准。Client 端只负责用户交互、页面展示、客户端状态管理、授权引导和接口调用，不负责主播状态探测、推送额度发放、开播判定、微信服务通知发送或任何需要服务端权威判断的业务逻辑。

本产品支持用户自定义添加抖音和哔哩哔哩主播进行监听。用户可以创建自己的 DIY 分类，将同一个主播放入多个个人分类；主播广场中的推荐内容属于公共内容，用户关注后仍需自行决定归入哪个个人分类。

---

## 2. 产品目标

Client 端的核心目标是让用户可以在尽可能少的操作步骤内完成「添加主播—授权提醒—等待开播—收到通知—进入直播间」的闭环。同时，用户应能清晰知道当前监听了哪些主播、哪些主播正在直播、订阅消息还剩多少可用额度、哪些提醒权限存在问题，以及如何自行修复。

### 2.1 核心目标

| 目标 | 说明 | 验收方向 |
|---|---|---|
| 快速添加 | 用户可以搜索主播、粘贴抖音分享文案或 B 站直播间链接 | 普通用户首次使用可在 1 分钟内完成添加 |
| 稳定查看 | 以分类方式查看自己的监听列表和主播状态 | 列表状态有更新时间，不让用户误认为绝对实时 |
| 明确授权 | 在合适的业务节点引导用户授权订阅消息 | 用户知道为什么授权、授权后能获得什么服务 |
| 自主管理 | 用户可以创建、编辑、删除、排序 DIY 分类 | 分类修改只影响当前用户，不影响全局主播 |
| 可排障 | 用户能自助检查订阅权限、发送测试推送、清理缓存 | 常见问题优先通过帮助中心解决 |
| 低打扰 | 核心功能不被广告或营销弹窗阻塞 | 开播提醒、状态查看、返回和退出流程顺畅 |

### 2.2 非目标

Client 端不负责调用抖音或 B 站接口，不在本地判断主播是否开播，不根据前端上报给用户增加推送次数，不保存微信 session_key、平台 Cookie 或探测凭证，不直接连接 MongoDB、Redis 或消息队列，也不直接操作微信服务端下发接口。

## 3. 用户与使用场景

### 3.1 用户角色

| 用户角色 | 特征 | 主要诉求 |
|---|---|---|
| 普通粉丝 | 监听 1 至 5 个主播 | 希望主播开播时收到提醒，操作简单 |
| 重度用户 | 监听多个平台、多个圈层主播 | 需要更多监听位、分类、批量操作和更长历史 |
| 新用户 | 尚未添加主播 | 需要从主播广场或搜索快速找到可监听主播 |

### 3.2 核心场景

用户第一次打开小程序后完成登录，进入监控首页。用户可以直接点击添加主播，也可以进入主播广场浏览推荐内容。添加主播时，用户搜索昵称、平台 ID，或粘贴分享链接，系统返回主播资料。用户确认关注后，可以选择已有个人分类、现场新建分类，或者暂时放入「未分类」。

添加完成后，客户端在合适的用户主动点击场景中请求订阅消息授权。用户同意后，服务端根据微信回调记录额度，客户端只刷新服务端返回的余额，不自行增加次数。主播开播后，用户通过微信服务通知收到提醒，点击通知卡片进入小程序直播详情页，再跳转到对应平台直播间。

## 4. Client 端职责边界

### 4.1 Client 端负责的事项

| 领域 | Client 端职责 |
|---|---|
| 页面展示 | 展示用户资料、主播列表、状态、分类、额度、推送记录和帮助内容 |
| 用户输入 | 接收关键词、平台 ID、直播间链接、分享文案、分类名称和设置项 |
| 交互校验 | 做必填、长度、格式、重复点击和明显非法输入校验 |
| 授权引导 | 在用户主动点击后调用订阅消息授权接口，并展示授权结果 |
| 本地体验 | 维护页面缓存、加载态、错误态、空状态和本地缓存清理 |
| 路由跳转 | 处理页面间跳转、推送卡片落地、平台直播间跳转 |
| 数据刷新 | 通过 API 获取权威数据，并在关键操作后刷新页面 |
| 埋点上报 | 上报页面访问、添加成功、分类操作、推荐点击等非敏感行为事件 |

### 4.2 Client 端不负责的事项

| 事项 | 责任归属 |
|---|---|
| 主播是否开播 | Server 的平台探测器和状态判定模块 |
| 轮询频率和队列调度 | Server Worker |
| 推送额度发放和扣减 | Server，以微信回调和服务端账本为准 |
| 微信服务通知发送 | Server 微信模块和推送 Worker |
| 用户权限最终判断 | Server 鉴权与权限模块 |
| 公共推荐内容维护 | Admin + Server |
| 用户数据持久化 | Server + MongoDB |
| 抖音/B站接口调用 | Server Crawler Provider |

## 5. 信息架构

小程序采用五个底部导航入口：监控、主播广场、直播回放、设置、帮助中心。添加主播、主播详情、分类管理、推送记录、增加授权次数等作为二级页面或弹层进入。

| 一级入口 | 主要页面 | 页面目的 |
|---|---|---|
| 监控 | 监听列表、分类筛选、添加主播、主播详情 | 查看我关注的主播和当前开播状态 |
| 主播广场 | 推荐专题、推荐主播、推荐详情 | 帮助用户发现可监听主播 |
| 直播回放 | 开播历史、单场详情 | 查看历史开播记录和直播信息 |
| 设置 | 推送设置、免打扰、模式设置 | 管理用户个人提醒偏好 |
| 帮助中心 | 权限诊断、测试推送、FAQ、缓存清理 | 解决订阅和页面使用问题 |

## 6. 页面 PRD

### 6.1 监控首页

**页面目标**：让用户一眼看到自己的监听主播、当前开播状态、剩余提醒额度和权限是否正常。

| 功能区 | 产品需求 |
|---|---|
| 顶部标题区 | 展示产品名称或当前页面标题；提供添加主播入口 |
| 分类导航 | 展示系统视图「全部」「未分类」和用户自建分类；显示每类主播数量；支持横向滚动或下拉选择 |
| 监听列表 | 展示头像、昵称、平台、平台 ID、直播状态、状态更新时间和个人分类标记 |
| 开播状态 | 正在直播使用明显状态样式；未开播显示最近更新时间；状态由服务端返回，客户端不得自行推断 |
| 单主播操作 | 进入详情、修改备注、调整分类、打开或关闭该主播提醒 |
| 总开关 | 控制用户整体开播提醒开关；关闭后不删除订阅关系 |
| 额度卡片 | 展示剩余可推送次数、授权状态和进入授权引导的入口 |
| 权限异常横幅 | 当服务端返回模板未授权、拒收或额度不足时展示对应提示和修复入口 |
| 空状态 | 没有监听主播时，引导添加主播或进入主播广场 |
| 下拉刷新 | 刷新当前分类和主播状态；不保证立即触发平台探测 |

**交互规则**：首次进入首页不自动弹订阅授权窗口。授权必须由用户点击明确按钮触发。监听列表默认按开播状态、用户排序值、添加时间排序，具体排序规则由 Server 返回结果控制或通过配置下发。

**验收标准**：用户可以在首页切换个人分类；每个分类展示正确数量；主播状态带更新时间；关闭单主播开关后页面状态立即更新；关闭总开关不删除主播；没有主播时有明确引导；请求失败时有重试入口。

### 6.2 添加主播页

**页面目标**：让用户通过搜索、平台 ID、直播间链接或分享文案添加主播。

| 功能 | 产品需求 |
|---|---|
| 平台选择 | 支持抖音、哔哩哔哩；平台选择影响输入提示和解析规则 |
| 关键词搜索 | 输入主播昵称、平台 ID；展示搜索结果和平台标识 |
| 链接解析 | 支持粘贴直播间链接、用户主页链接或抖音分享文案；由 Server 解析，不在 Client 端实现平台规则 |
| 结果确认 | 展示主播昵称、头像、平台 ID、直播间链接和当前直播状态 |
| 关注确认 | 用户点击关注后，弹出分类选择；可选择已有分类、创建新分类或跳过归入未分类 |
| 重复关注 | 如果用户已经关注，展示“已关注”并允许进入详情或修改分类，不重复创建关系 |
| 解析失败 | 说明平台暂不支持、链接无效、主播不存在、平台风控或服务暂时不可用 |
| 历史搜索 | 可保留最近搜索关键词，但不得默认保存敏感剪贴板内容 |

**验收标准**：合法的 B 站链接和支持的抖音分享文案能够返回解析结果；重复添加不会产生重复订阅；添加成功后列表和分类数量同步更新；解析失败不会创建脏主播记录。

### 6.3 主播广场

**页面目标**：提供公共推荐，帮助新用户发现主播，但不替用户管理个人分类。

| 功能区 | 产品需求 |
|---|---|
| 推荐专题 | 展示后台配置的推荐专题、专题标题、简介、封面和排序 |
| 推荐列表 | 展示主播昵称、头像、平台、当前状态、推荐理由和关注状态 |
| 一键关注 | 用户关注后弹出个人分类选择，不自动使用后台专题名称作为用户分类 |
| 已关注标记 | 如果用户已关注，展示已关注并允许进入详情 |
| 推荐统计 | Client 上报曝光、点击、关注等行为，Server 负责聚合，Admin 查看统计 |
| 下架处理 | 后台下架后，客户端不再展示；已关注关系不受影响 |

**验收标准**：后台推荐专题能按配置展示；推荐主播支持抖音和 B 站；关注后用户可以选择自己的分类；推荐排序不会改变用户已有分类。

### 6.4 主播详情页

**页面目标**：展示主播的公开资料、当前状态、历史开播记录和当前用户的关注配置。

页面应展示主播头像、昵称、平台、平台 ID、直播间链接、当前直播状态、直播标题、封面、最近开播时间和关注人数等公开信息。已关注用户可以修改提醒开关、备注和分类；未关注用户可以直接关注。

当用户从服务通知进入详情页时，应优先展示对应的开播会话信息，包括主播、平台、开播时间、直播标题和“进入直播间”按钮。跳转平台前应明确提示用户即将离开小程序或打开对应平台页面。

### 6.5 分类管理页

**页面目标**：完全由用户管理自己的 DIY 分类。

| 功能 | 产品需求 |
|---|---|
| 系统视图 | 固定提供「全部」和「未分类」，不可删除 |
| 创建分类 | 输入分类名称，可选颜色和图标；校验同一用户下重名和数量上限 |
| 编辑分类 | 修改名称、颜色、图标、排序 |
| 删除分类 | 只删除分类关系，不删除主播和监听关系；关联主播回到未分类 |
| 排序 | 支持拖动排序或上移下移 |
| 批量归类 | 选择多个监听主播加入一个或多个分类 |
| 移出分类 | 从当前分类中移除主播，但不取消监听 |
| 分类为空 | 展示空状态和批量归类入口 |

同一个主播可以同时属于多个分类。分类数据属于当前用户，Client 只提交用户的分类操作，最终权限和数据完整性由 Server 校验。

### 6.6 直播回放页

页面展示历史开播会话，支持按平台、主播、分类和时间筛选。用户可以查看主播、开播时间、结束时间、直播标题、封面和直播时长；是否能进入平台回放由 Server 根据平台公开链接返回结果决定。没有回放链接时，只展示历史记录，不显示无效跳转按钮。

### 6.7 设置页

| 设置项 | 交互要求 |
|---|---|
| 开播提醒总开关 | 关闭后停止该用户的开播通知，但保留监听数据 |
| 单主播提醒开关 | 在首页或详情页独立控制 |
| 免打扰 | 支持开启、开始时间、结束时间；跨午夜场景要有明确提示 |
| 仅推送大号 | 依赖后台主播标签；未标注时提示可能无法准确筛选 |
| 学生党模式 | 根据服务端节假日配置控制提醒；客户端展示规则说明 |
| 默认分类 | 新增监听时默认选择的分类，可设为未分类 |
| 数据清理 | 清理本地缓存，不删除服务端账号、分类和监听数据 |

### 6.8 帮助中心

帮助中心必须提供四项自助诊断：检查订阅权限、发送测试推送、清除通知缓存、清除本地缓存。还应提供订阅消息为什么不弹窗、为什么没有收到提醒、为什么状态有延迟、为什么只有进入微信后才看到通知、如何恢复拒收权限等 FAQ。

测试推送按钮必须明确说明测试消息不代表真实开播提醒，发送结果以服务端返回为准。清除本地缓存只影响设备本地数据，不得让用户误以为服务端数据被删除。

### 6.9 推送记录页

推送记录展示主播、平台、开播时间、推送时间、状态、失败或跳过原因。状态至少包含待发送、已发送、已送达、失败、跳过。对于“额度不足、免打扰、主播提醒关闭、用户拒收”等情况，应展示用户能理解的说明，不直接暴露内部错误堆栈。

### 6.10 增加授权次数页

该页面用于引导用户主动授权一次性订阅消息。页面需展示当前余额、每次授权对应的提醒服务、上限说明和授权入口。Client 只能发起授权和刷新余额，不能自行增加余额，也不能把授权次数描述为付费商品或绝对送达承诺。

## 7. Client 端接口依赖

所有接口由 Server 提供，Client 使用统一请求封装和 JWT。接口返回的业务状态以 Server 为准，Client 只负责展示。

| 方法 | API | Client 使用场景 |
|---|---|---|
| POST | `/api/v1/auth/login` | 小程序登录换取自有令牌 |
| GET | `/api/v1/user/profile` | 首页初始化用户、额度、授权状态 |
| PUT | `/api/v1/user/settings` | 保存推送和模式设置 |
| GET | `/api/v1/anchors/search` | 搜索主播 |
| POST | `/api/v1/anchors/resolve` | 解析粘贴链接或分享文案 |
| GET | `/api/v1/anchors/pool` | 获取主播广场推荐内容 |
| GET | `/api/v1/anchors/:id` | 获取主播详情 |
| GET | `/api/v1/subscriptions` | 获取监听列表和状态 |
| POST | `/api/v1/subscriptions` | 添加监听 |
| PATCH | `/api/v1/subscriptions/:id` | 修改单个监听配置 |
| DELETE | `/api/v1/subscriptions/:id` | 取消监听 |
| POST | `/api/v1/subscriptions/batch` | 批量开关和批量归类 |
| GET/POST/PATCH/DELETE | `/api/v1/categories` | 分类查询、创建、修改、删除 |
| POST | `/api/v1/categories/:id/subscriptions` | 批量加入或移出分类 |
| GET | `/api/v1/quota` | 查询额度 |
| POST | `/api/v1/quota/refresh` | 授权后刷新额度 |
| GET | `/api/v1/notify/logs` | 查询推送记录 |
| POST | `/api/v1/notify/test` | 发送测试推送 |
| GET | `/api/v1/diagnose/auth` | 检查订阅权限 |
| POST | `/api/v1/diagnose/clear-cache` | 清理服务端授权镜像或通知缓存 |
| GET | `/api/v1/live/sessions` | 查询历史开播记录 |
| GET | `/api/v1/help/faq` | 获取 FAQ |
| GET | `/api/v1/config/app` | 获取客户端开关、公告和版本配置 |

## 8. 状态、异常和体验要求

| 场景 | Client 处理 |
|---|---|
| 首次加载 | 展示骨架屏；接口超时提供重试；不得长期停留空白页 |
| 未登录 | 进入登录引导；登录失败展示原因和重试入口 |
| 主播解析失败 | 展示具体原因，保留输入内容，允许重新解析 |
| 主播已失效 | 展示账号可能注销或平台暂时不可用，不自动删除用户监听 |
| 探测状态过期 | 展示最近更新时间和“数据可能延迟”提示 |
| 网络断开 | 使用最近一次缓存数据并标明离线状态，恢复网络后自动刷新 |
| 订阅被拒收 | 展示修复路径，引导用户前往微信设置，不反复弹窗骚扰 |
| 额度不足 | 引导授权，不展示“服务故障” |
| 推送未送达 | 推送记录展示可理解的失败原因，提供帮助入口 |
| 操作重复提交 | 按钮进入 loading，服务端幂等，客户端不重复创建 |
| 本地数据损坏 | 提供清除本地缓存入口，服务端数据不受影响 |

## 9. 埋点与产品指标

Client 需要上报不包含敏感内容的行为事件，包括首次打开、登录成功、搜索主播、解析成功、关注成功、分类创建、分类删除、推荐点击、推荐关注、授权按钮点击、授权结果刷新、帮助中心入口点击、测试推送点击和推送卡片进入详情页。

| 指标 | 目的 |
|---|---|
| 首次添加主播成功率 | 衡量上手链路 |
| 添加后授权点击率 | 衡量授权引导效果 |
| 订阅授权接受率 | 判断模板和交互是否合理 |
| 首次提醒成功率 | 验证核心价值 |
| 7 日留存 | 验证长期使用价值 |
| 人均监听主播数 | 判断容量上限设计 |
| 分类使用率 | 判断 DIY 分类价值 |
| 推荐点击到关注转化率 | 判断主播广场效果 |
| 帮助中心问题点击排行 | 指导产品和客服优化 |

Client 不采集手机号、通讯录、定位、私信、平台 Cookie 等与核心功能无关的数据。

## 10. Client 端版本范围

### V1 必须完成

登录、监控首页、添加主播、抖音和 B 站入口、主播详情、用户 DIY 分类、单主播开关、推送总开关、订阅授权引导、额度展示、推送记录、设置、帮助中心、测试推送入口、基础埋点和错误提示。

### V1.1 建议完成

主播广场推荐专题、批量归类、批量开关、直播回放筛选、更多 FAQ、用户数据导出入口、公告和客户端动态配置。

### 后续版本

团队共享分类、多人协作、更多平台、智能开播时间预测、第三方日历联动和商业会员相关页面。商业付费页面必须等主体、支付资质和平台审核路径确认后再进入需求排期。

## 11. Client 端验收标准

产品验收以用户能否独立完成完整闭环为核心。测试人员应能够完成登录、搜索或粘贴链接添加主播、创建分类、将主播放入分类、关闭单主播提醒、开启免打扰、发起订阅授权、查看剩余额度、发送测试推送、查看推送记录、从服务通知进入主播详情，并在清理本地缓存后重新从服务端恢复分类和监听数据。

所有页面必须覆盖加载中、空数据、网络失败、权限失败和接口异常状态。用户分类操作不能影响全局主播数据，主播广场推荐调整不能改变用户既有分类，Client 不能通过任何接口参数自行增加额度或伪造开播状态。

---

## 12. 与其他端的交付边界

Client 需要 Server 提供稳定的用户、主播、分类、订阅、额度、推送记录和推荐内容接口；Server 需要 Client 明确提交用户操作的业务意图和必要参数；Admin 不直接依赖 Client 的本地数据，所有后台数据均来自 Server。

Client 的完成标志不是“页面全部做完”，而是用户可以顺利完成业务闭环，并且所有权威数据由 Server 保存、所有运营内容由 Admin 配置。
