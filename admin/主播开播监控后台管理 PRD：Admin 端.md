# 主播开播监控后台管理 PRD：Admin 端

**文档版本**：V1.0
**编制日期**：2026 年 8 月 19 日
**技术栈**：Vue3 + TypeScript + Ant Design Vue，建议基于 vue-vben-admin 5 的 Ant Design Vue 版本
**服务对象**：产品运营、用户支持、内容运营、系统运维、超级管理员
**后端依赖**：NestJS Admin API、MongoDB、Redis、BullMQ、Provider 监控服务

---

## 1. 文档说明

本 PRD 定义主播开播监控后台管理系统的角色、菜单、页面、数据范围、操作权限、审计规则、监控指标和验收标准。Admin 的核心目标不是替代 Client，而是为运营、用户支持和系统维护人员提供可控、可审计的管理工具。

Admin 负责管理公共主播池、主播广场推荐、用户业务数据查看、额度和推送问题处理、Provider 运维、队列和系统监控。Admin 不直接连接 MongoDB、Redis 或外部平台，不直接调用微信发送接口，所有操作都通过 Server Admin API 完成。

用户的关注主播和 DIY 分类属于用户业务数据，服务端需要保存，后台也应保留用户列表和用户详情查看能力。第一版默认允许后台只读查看用户关注主播、分类、订阅状态和推送记录，但不允许普通管理员代替用户创建、删除、移动分类或修改关注关系。

---

## 2. 后台目标

| 目标 | 说明 |
|---|---|
| 用户支持 | 能快速查询用户、关注主播、个人分类、额度、推送记录和失败原因 |
| 主播运营 | 管理公共主播池、标签、探测层级和主播有效性 |
| 推荐运营 | 管理主播广场推荐专题、推荐主播、推荐理由和排序 |
| 推送排障 | 查询每次推送的状态、微信错误码、异步回执和跳过原因 |
| Provider 运维 | 观察 B 站、抖音探测链路健康度、失败率、熔断和降级状态 |
| 系统监控 | 监控队列积压、API、MongoDB、Redis、推送和探测延迟 |
| 权限审计 | 按角色限制数据和操作，并保存所有高风险操作记录 |

## 3. Admin 端职责边界

### 3.1 Admin 端负责

| 领域 | Admin 职责 |
|---|---|
| 用户管理 | 用户列表、用户详情、用户关注主播、个人分类、订阅状态和推送记录查看 |
| 用户支持 | 封禁/解封、额度调整、测试推送、问题定位、必要的账号状态处理 |
| 主播池 | 公共主播新增、编辑、停用、平台标签、探测层级和手动探测 |
| 推荐内容 | 推荐专题、推荐主播、推荐理由、排序和上下架 |
| 推送审计 | 推送日志查询、失败分析、授权状态核对和受控补发 |
| Provider 运维 | 健康状态、成功率、耗时、熔断和降级策略 |
| 系统监控 | 队列、API、数据库、缓存、任务和告警 |
| 配置管理 | 轮询间隔、限流阈值、模板 ID、额度上限和功能开关 |
| 审计 | 记录管理员登录、查询敏感数据和所有写操作 |

### 3.2 Admin 端不负责

| 事项 | 责任归属 |
|---|---|
| 用户自己创建和修改分类的正常操作 | Client + Server |
| 主播是否开播的判断 | Server Worker + Provider |
| 微信订阅弹窗 | Client 调起微信能力 |
| 微信订阅额度的自然发放 | 微信回调 + Server |
| 直接修改数据库 | 禁止，必须通过 Server API |
| 直接调用抖音/B站接口 | Server Crawler Provider |
| 直接发送微信服务通知 | Server Notify Worker |

## 4. 角色与权限

### 4.1 角色定义

| 角色 | 主要职责 | 默认数据范围 |
|---|---|---|
| 超级管理员 | 系统全量管理和高风险操作 | 全部业务数据和系统配置 |
| 用户支持 | 处理用户账号、推送和额度问题 | 用户列表、用户详情、关注主播、分类、推送记录 |
| 内容运营 | 管理公共主播和主播广场推荐 | 公共主播池、推荐内容、汇总转化数据 |
| 运维审计 | 处理服务运行和审计问题 | 系统指标、队列、Provider、操作日志；默认不开放用户详情 |
| 只读观察员 | 查看业务和运营数据 | 按授权范围只读 |

### 4.2 权限矩阵

| 功能 | 超级管理员 | 用户支持 | 内容运营 | 运维审计 | 只读观察员 |
|---|---|---|---|---|---|
| 查看用户列表 | 是 | 是 | 否 | 默认否 | 可配置 |
| 查看用户关注主播 | 是 | 是 | 否 | 默认否 | 可配置 |
| 查看用户个人分类 | 是 | 是，只读 | 否 | 默认否 | 默认否 |
| 修改用户分类 | 受控 | 否 | 否 | 否 | 否 |
| 封禁/解封用户 | 是 | 受控 | 否 | 否 | 否 |
| 调整用户额度 | 是 | 受控 | 否 | 否 | 否 |
| 发送测试推送 | 是 | 是 | 否 | 否 | 否 |
| 补发正式推送 | 是 | 受控 | 否 | 否 | 否 |
| 管理公共主播池 | 是 | 否 | 是 | 否 | 否 |
| 管理推荐内容 | 是 | 否 | 是 | 否 | 否 |
| 修改探测配置 | 是 | 否 | 否 | 受控 | 否 |
| 查看 Provider 凭证摘要 | 是 | 否 | 否 | 是 | 否 |
| 查看完整敏感凭证 | 原则上否 | 否 | 否 | 否 | 否 |
| 查看系统监控 | 是 | 部分 | 部分 | 是 | 可配置 |
| 管理后台账号 | 是 | 否 | 否 | 否 | 否 |
| 查看操作审计 | 是 | 受限 | 否 | 是 | 否 |

“修改用户分类”即使超级管理员也不建议作为常规操作开放。第一版可以预留受控能力，但默认关闭；未来如果需要客服代操作，必须要求操作原因、二次确认、前后差异、操作人和用户通知。

## 6. 工作台 PRD

### 6.1 页面目标

工作台用于让管理员进入后台后快速判断系统是否正常、今天是否有异常、用户支持是否有待处理事项。页面不展示未经授权的完整用户隐私字段。

### 6.2 指标卡片

| 指标 | 说明 |
|---|---|
| 今日开播会话数 | 按平台统计今日确认的直播场次 |
| 今日推送数 | 已进入发送流程的通知数量 |
| 推送成功率 | 按同步结果和最终回执计算 |
| Provider 成功率 | B 站、抖音各 Provider 成功率 |
| 当前队列积压 | 各队列等待任务和失败任务 |
| 活跃用户数 | 按日/周/月统计活跃用户 |
| 活跃监听主播数 | 当前至少有一个启用订阅的主播数 |
| 订阅权限异常用户数 | 最近授权失败或拒收的用户数 |

### 6.3 待处理事项

工作台展示 Provider 熔断、微信 token 失效、推送失败激增、队列积压、额度对账差异、主播连续失效、服务器磁盘或 Redis/MongoDB 异常等告警。每个告警都应包含级别、发生时间、影响范围、当前状态和进入详情按钮。

## 7. 用户管理 PRD

### 7.1 用户列表

用户列表是后台的基础功能，必须保留用户业务数据查看能力。

| 字段 | 说明 | 默认展示 |
|---|---|---|
| 内部用户编号 | 系统 userId 或可读短编号 | 是 |
| 微信昵称、头像 | 只有用户授权后才有 | 是 |
| 脱敏 openid | 不展示完整 openid | 是 |
| 注册时间 | 用户首次登录时间 | 是 |
| 最近活跃时间 | 最近一次访问或 API 活动时间 | 是 |
| 关注主播数 | 当前启用或全部订阅数，可切换口径 | 是 |
| 分类数 | 用户 DIY 分类数量 | 是 |
| 未分类主播数 | 没有分类关系的订阅数量 | 是 |
| 剩余提醒次数 | 当前额度余额 | 受权限控制 |
| 最后推送时间 | 最近一次推送时间和状态 | 是 |
| 用户状态 | 正常、禁用、注销中 | 是 |

列表支持按用户编号、昵称、脱敏 openid、状态、注册时间、活跃时间、关注数量和推送异常筛选。所有分页和搜索由 Server 完成，Admin 不下载全量用户数据到浏览器。

### 7.2 用户详情

用户详情使用页签展示，至少包含以下内容。

| 页签 | 内容 | 操作限制 |
|---|---|---|
| 基础资料 | 内部编号、脱敏 openid、昵称、头像、注册时间、最近活跃、状态 | 可查看；修改状态需权限 |
| 关注主播 | 平台、主播昵称、直播状态、监听开关、所属分类、备注、添加时间、最近提醒 | 默认只读；可进入主播详情 |
| 个人分类 | 分类名称、颜色、图标、排序、分类下主播数量和主播明细 | 默认只读；不可代替用户修改 |
| 额度流水 | 当前余额、发放、消耗、返还、后台调整记录 | 额度调整需权限和原因 |
| 推送记录 | 主播、开播会话、推送状态、微信错误码、跳过原因、消息 ID | 支持查看和受控补发 |
| 操作日志 | 后台查看、封禁、额度调整、补发、备注等动作 | 只追加，不允许修改 |

用户详情必须避免暴露其他用户的数据。用户支持人员只能通过脱敏信息定位用户，查看权限和操作均计入审计日志。

### 7.3 用户状态操作

| 操作 | 需求 |
|---|---|
| 封禁用户 | 需要选择原因；封禁后阻止新增订阅和推送；保留数据用于申诉和审计 |
| 解封用户 | 需要权限；恢复前检查是否存在异常行为 |
| 注销处理 | 接收用户注销请求，展示处理状态，不允许后台直接物理删除未确认数据 |
| 调整额度 | 输入正负变化值和原因；写入额度账本；不允许直接改余额快照 |
| 测试推送 | 发送测试消息，不影响用户正常业务额度；记录测试结果 |
| 查看帮助 | 为客服展示针对当前用户的订阅修复和推送排障建议 |

## 8. 公共主播池管理 PRD

### 8.1 页面目标

公共主播池是所有用户共同使用的主播基础数据和探测目标。后台可以维护主播公开资料和探测运营属性，但不能把用户个人分类写入主播池。

### 8.2 主播列表

列表展示平台、主播昵称、平台 ID、直播间号、当前状态、关注人数、探测层级、探测间隔、最近探测时间、最近成功时间、连续失败次数、当前 Provider 和账号状态。

支持按平台、状态、探测层级、关注人数、连续失败次数、Provider、是否推荐和更新时间筛选。

### 8.3 主播详情和操作

| 操作 | 产品需求 |
|---|---|
| 新增主播 | 通过平台和稳定 ID 或链接解析加入公共池 |
| 编辑公开资料 | 修正昵称、头像、直播间链接和公开标签；必要时触发资料刷新 |
| 维护标签 | 维护大号、官方、重点监控等平台或运营标签 |
| 设置探测层级 | 热门、普通、冷门、暂停；支持调整间隔 |
| 手动探测 | 触发一次探测，展示归一化结果、Provider 和耗时；原始响应仅限高权限查看 |
| 暂停探测 | 暂停后不再进入轮询，必须填写原因 |
| 标记失效 | 账号注销、房间不存在、平台限制等；不删除历史会话 |
| 恢复主播 | 重新加入探测任务，清理或保留失败计数由 Server 规则决定 |

后台编辑公共主播资料会影响所有用户的展示，但不应覆盖平台自动刷新得到的字段。需要区分平台原始资料、后台人工覆盖值和最终展示值。

## 9. 主播广场推荐管理 PRD

### 9.1 推荐专题

内容运营可以创建推荐专题，填写专题名称、简介、封面、展示时间、排序、状态和推荐规则。专题支持草稿、待发布、已发布、已下架四种状态。

### 9.2 推荐主播

在专题下选择公共主播，设置推荐顺序、推荐理由、展示标签和是否置顶。推荐主播必须已经存在于公共主播池，不能在推荐页面创建孤立主播。

### 9.3 推荐与用户数据边界

推荐专题是公共内容，用户关注后形成自己的 subscription；后台修改推荐专题、排序或下架，不得删除用户关注关系，不得修改用户个人分类。后台可以查看推荐曝光、点击、关注转化等汇总数据，但内容运营默认不能查看用户具体分类。

### 9.4 推荐合作

如果未来出现商业推荐，需要单独增加“合作推荐”标识、合作方、授权材料、开始和结束时间、素材来源、投诉入口和下架动作。不能未经授权使用主播名称、头像、商标或暗示官方合作关系。

## 10. 推送管理 PRD

### 10.1 推送日志列表

推送日志支持按用户、主播、平台、开播会话、时间、状态、错误码、跳过原因和模板 ID 查询。列表展示推送任务状态、创建时间、发送时间、最终回执时间、耗时和额度处理结果。

### 10.2 推送详情

推送详情展示用户脱敏标识、主播、开播会话、实际模板、服务通知字段摘要、同步错误码、异步回执、重试次数、额度扣减/返还结果和责任链路。完整 payload 只对具备权限的用户支持角色开放，且敏感字段脱敏。

### 10.3 受控补发

补发只允许对明确失败或因系统异常跳过的记录执行，不允许对用户明确拒收、免打扰或主动关闭订阅的记录强制发送。补发前需要展示原因、原推送状态和预计是否消耗额度；操作人必须填写补发理由。补发任务使用新的幂等键，但关联原推送记录。

### 10.4 模板配置

后台可以配置模板 ID、模板字段映射、字段长度限制、跳转页面、开发版/体验版/正式版状态和启用状态。模板变更需要超级管理员权限，并记录变更前后值。未发布或未验证的模板不能切换为正式发送模板。

---

## 11. Provider 运维 PRD

### 11.1 Provider 状态

展示每个平台每个 Provider 的健康状态、成功率、失败率、平均耗时、P95 耗时、最近成功时间、最近失败原因、当前熔断状态和最近降级次数。

### 11.2 操作能力

| 操作 | 要求 |
|---|---|
| 手动健康检查 | 选择平台和 Provider，执行一次检查并记录结果 |
| 调整优先级 | 只有运维或超级管理员可操作，变更记审计 |
| 开关 Provider | 关闭前提示影响范围，关闭后自动降级 |
| 调整限流 | 需要填写原因和生效时间；高风险配置需二次确认 |
| 查看凭证池状态 | 只展示数量、有效期、成功率和脱敏标识 |
| 重置熔断 | 需要权限和原因，不能绕过连续失败事实 |
| 查看原始响应 | 仅超级管理员或指定运维权限；必须短期、脱敏、审计 |

后台不展示完整 Cookie、签名参数、session_key 或其他敏感凭证。抖音 Provider 失败时，应明确显示“探测失败/已降级”，不能直接显示“主播未开播”以免误导运营。

## 12. 监控大盘和告警

### 12.1 业务指标

| 看板 | 指标 |
|---|---|
| 用户看板 | 新增用户、活跃用户、留存、用户状态分布、监听主播数分布 |
| 监听看板 | 启用订阅数、平台分布、分类使用率、未分类数量、人均监听数 |
| 开播看板 | 开播会话数、平台分布、开播时段、探测延迟、疑似误报 |
| 推送看板 | 发送数、成功数、失败数、跳过数、错误码排行、额度消耗 |
| 推荐看板 | 专题曝光、点击、关注转化、已关注用户占比 |
| 系统看板 | API、队列、MongoDB、Redis、Provider、服务器资源 |

### 12.2 告警规则

| 告警 | 触发方向 | 处理入口 |
|---|---|---|
| Provider 连续失败 | 同 Provider 连续超过阈值 | Provider 运维 |
| 抖音降级比例过高 | 签名直连大量失败 | Provider 运维 |
| 微信 token 失效 | 40001 集中出现 | 微信配置/运维 |
| 推送成功率下降 | 同时间段异常下降 | 推送审计 |
| 队列积压 | 等待任务超过阈值 | 队列监控 |
| 额度对账差异 | 账本与快照不一致 | 额度审计 |
| 数据库慢查询 | 超过配置耗时 | 运维 |
| 磁盘或内存不足 | 达到资源阈值 | 运维 |

## 13. 系统设置和配置中心

配置中心只对有权限的角色开放，所有配置需要显示当前值、修改人、修改时间、影响范围和恢复默认值入口。

| 配置项 | 示例 |
|---|---|
| 轮询间隔 | 热门、普通、冷门主播间隔 |
| 平台限流 | B 站、抖音各 Provider QPS |
| Provider 优先级 | 签名、浏览器、第三方 |
| 熔断规则 | 失败次数、熔断时长、恢复条件 |
| 防抖规则 | 二次确认延迟、下播连续次数、重播冷却 |
| 额度上限 | 用户余额上限、模板额度上限 |
| 订阅数量限制 | 免费用户和不同等级用户的订阅上限 |
| 模板配置 | 模板 ID、字段映射、页面路径、环境 |
| 功能开关 | 推荐广场、抖音 Provider、测试推送等 |
| 数据保留 | 推送日志、调试响应、统计数据保留周期 |

高风险配置变更需要二次确认，配置生效失败时必须保留原配置并告警。

## 14. 审计和数据安全

### 14.1 必须审计的操作

管理员登录、查看敏感用户详情、查看具体分类、查看推送 payload、额度增加或扣减、封禁/解封、测试推送、正式补发、主播停用/恢复、Provider 开关、限流调整、模板切换、推荐内容发布和后台账号权限变更都必须写入 audit_logs。

### 14.2 审计字段

审计记录至少包含操作人、角色、操作类型、业务对象类型、业务对象 ID、操作原因、操作前摘要、操作后摘要、请求 IP、User-Agent、traceId、结果和创建时间。审计记录只允许追加，不允许普通管理员修改或删除。

### 14.3 用户数据访问原则

后台可以保留并查看用户列表、关注主播、分类和推送记录，但默认按最小权限展示。openid 脱敏，敏感字段不出现在前端源码和浏览器本地长期存储中。内容运营只看公共推荐和汇总转化，不看用户具体分类；运维默认不看用户业务数据。

## 16. Admin 端验收标准

管理员可以按权限登录后台；不同角色只能访问授权菜单；用户列表支持搜索、分页和脱敏展示；用户详情能查看关注主播、个人分类、额度流水、推送记录和操作日志；普通管理员不能代替用户修改分类；额度调整会写入账本并记录审计；公共主播编辑不会修改用户私有分类；推荐内容上下架不会删除用户关注关系；推送详情能关联开播会话和微信错误码；补发必须有权限和原因；Provider 失败、熔断和降级状态可查看；队列积压和推送失败可以在工作台或监控页发现；所有高风险操作都有操作人、原因、时间和结果。

后台验收还要覆盖权限反向测试：用户支持不能管理 Provider；内容运营不能查看用户具体分类；运维审计不能默认查看用户详情；只读观察员不能执行任何写操作；被禁用的管理员立即失去后台 API 权限。

---

## 17. 与 Client、Server 的交付边界

Client 负责用户端体验和用户主动操作；Server 负责所有业务权威判断、数据存储、探测、推送和 Admin API；Admin 负责运营和运维操作，不直接访问数据库和平台接口。

Admin 的完成标志不是“后台页面多”，而是出现问题时能够回答三个问题：哪个用户受影响、哪一步失败、管理员能否在不破坏用户数据的情况下处理。
